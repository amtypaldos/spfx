# ADR-003: Persistent configuration

- Location: **two 4 KB internal-flash pages inside our own app region** (not the 0xFF000 page that the upstream board file reserves as `storage`), so nothing outside our image is touched. **Addresses (set 2026-11-24, zephyr_sp1fx v1-rc1): 0xFD000-0xFDFFF and 0xFE000-0xFEFFF**, the last two pages of the board's slot0 (0x20000-0xFEFFF). The app overlay shortens `slot0_partition` to 0x20000-0xFCFFF (the linker refuses a bigger image) and adds `sp1fx_config_partition` at 0xFD000 (size 0x2000); compile-time asserts in `firmware/app/zephyr_sp1fx/src/main.c` pin both and the untouched `storage_partition` at 0xFF000; every flash read/write/erase goes through one range check that refuses anything outside the two pages; `check_image.py --reserve 0xFD000:0xFF000` fails a build whose image reaches them. Verified against `firmware/boards/teenageengineering/stem_player/stem_player.dts` (boot 0x0-0x1FFFF, slot0 0x20000-0xFEFFF, storage 0xFF000-0xFFFFF) and the generated `zephyr.dts` of the build. (Source/build finding; nothing written on hardware yet.)
- eMMC is **not used** for settings; the user's Tape Looper library lives there.
- Record: 512 B (magic, layout version, length, sequence, payload, CRC-32), 8 per page, append-only; newest valid sequence wins; a page is erased only when the other page holds the newest record.
- Payload: layout v1 in `firmware/storage/config_store.c` (also reused by the protocol STATE message). Floats are stored as 16-bit fixed point. Remembered parameters for every effect in every slot are kept. Unknown future layouts fall back to defaults.
- Wear: one save per 1.5 s of quiet and at most one per 5 s. 8 saves per page, two pages: one page erase per 8 saves (an already-blank page is not erased again). nRF52840 flash is rated for 10,000 erase cycles per page (datasheet figure, not verified here), so well over 100,000 saves.
- Never called from the audio thread. Erase stalls the CPU on nRF52840 (the flash controller halts bus access for up to ~85 ms per page erase); the firmware must perform erases while audio is muted or in a thread that tolerates the stall.
  - **Zephyr behaviour (source finding, Zephyr v4.3.1 `drivers/flash/soc_flash_nrf.c`):** without a radio stack the driver is built with `SOC_FLASH_NRF_RADIO_SYNC_NONE` (confirmed in the build's `.config`); `flash_erase` then calls `nrfx_nvmc_page_erase` once per page and waits: one blocking stall, no partial erase. `flash_write` writes word by word (`nrfx_nvmc_word_write`, up to 41 us stall each) without yielding.
  - **Policy (zephyr_sp1fx):** writes are issued 8 bytes at a time with a 0.4 ms sleep between them (stalls <= ~82 us; USB SOF and I2S servicing continue). Erases run only (a) ahead of time on the spare page (`store_erase_spare`, so normal saves never erase) while the audio has been quiet for 1.5 s (input and output below -66 dBFS, config settled), (b) for a save that cannot avoid one, also only while quiet, (c) at FN-hold power off, (d) on the companion's explicit SAVE_NOW. Every erase first ducks the output to silence. A save that needs an erase while music plays waits in RAM. Decision logic: `firmware/app/app_logic.c` (host-tested with the real journal: zero erases while audio is audible over a simulated 2 h session).
  - **Still unmeasured on the device:** actual erase/write times and whether any audible artefact remains (the console prints `FLASH erase ... took N ms` and `write_ms_max`).
- Tested on the host with a NOR-semantics mock flash, power loss injected at every 7th byte of a record write, an interrupted erase, bit flips and fully corrupted pages.
